# 专业覆盖层

覆盖层不是第二套完整模板。生成 Requirement 时，把对应专业要求合并进基础模板；共同背景、前置、禁令与交回格式仍使用基础模板。

## `[原始需求]` 覆盖层

- **身份**：需求负责人和变更控制人。
- **必须写入**：用户原始描述、来源与日期、附件清单、讨论后锁定的目标/范围/非目标、涉及工种、冲突处理、变更影响规则。
- **交付**：后续专业单可引用的需求源真值；变更时输出受影响单据清单，不静默改写下游决定。

## `[策划]` 覆盖层

- **身份**：产品负责人、制作人或游戏策划。
- **详细要求**：用户与场景、价值、术语、主流程、状态与权限、业务规则、内容合同、范围与非目标、人工确认点、成功指标。
- **交付**：PRD/规则表/流程与状态说明，以及可供设计、QA 和程序消费的锁定决定。

## `[UX/UI]` 覆盖层

- **身份**：UX 架构师与 UI 设计师。
- **详细要求**：信息架构、逐屏用户流、路由、核心交互、loading/empty/error/disabled/no-permission 等完整状态、文案、响应式、键盘与可访问性。
- **交付**：设计源、组件/页面状态表、交互说明与设计偏离规则，足以让 QA 写用例和程序还原。

## `[美术]` 覆盖层

- **身份**：游戏美术负责人或视觉资产负责人。
- **详细要求**：风格支柱、资产清单、尺寸/格式/色彩/性能规格、制作批次、验收参考、原创与授权边界。
- **交付**：可生产的美术 Brief、资产表、导出规则和评审标准；没有美术资产时不创建本单。

## `[测试·用例]` 覆盖层

- **身份**：QA 测试设计负责人。
- **详细要求**：在代码前把需求和设计转换成可执行用例，覆盖正常链、边界、权限、失败恢复、并发/幂等、兼容、视觉、可访问性、集成、E2E 与回归中的适用部分。
- **交付**：用例矩阵、fixture/环境要求、自动化层级映射、阻断条件和最终收尾清单。

## `[程序·协议/公共]` 覆盖层

- **身份**：技术负责人和共享合同维护者。
- **详细要求**：锁定 API/DTO、客户端-服务端协议、数据模型、公共接口、错误语义、鉴权、版本与兼容策略、共享测试夹具。
- **交付**：下游可直接消费的稳定接口及合同测试；不得同时夹带具体业务功能。

## `[程序·服务端]` 覆盖层

- **身份**：服务端工程师。
- **详细要求**：领域规则、存储与事务、鉴权、错误、日志、可观测性、迁移和服务端测试；遵守目标仓库合同真值与数据隔离规则。
- **TDD**：先实现对应 QA 用例的失败测试，再写最小服务端实现。

## `[程序·客户端]` 覆盖层

- **身份**：客户端或前端工程师。
- **详细要求**：消费已锁协议与设计，覆盖状态管理、交互反馈、错误可见性、缓存/同步、响应式、可访问性和客户端测试。
- **TDD**：先把对应 QA 用例落实为失败的 model/component/interaction 测试，再实现。

## `[程序·功能]` 覆盖层

- **身份**：负责明确业务切片的程序工程师。
- **边界**：一张卡只交付一个可独立验证的功能切片，写清文件集和消费/产出接口；同 wave 文件集不得重叠。
- **TDD**：失败测试必须因目标行为尚未实现而失败；实现后提交测试命令、结果与自审证据，不逐卡请求 reviewer。

## `[Review]` 覆盖层

- **身份**：未参与实现的整体代码 reviewer。
- **输入**：全部专业 Requirement、QA 测试合同、完整交付报告、基线到交付点的完整 diff 和验证证据。
- **详细要求**：对需求满足度、正确性、安全、合同、数据边界、错误处理、测试有效性和知识同步做对抗审查。
- **交付**：放行或退回结论、分级 findings、证据核验；不直接改代码。阻断问题集中进入一个修复 wave。

## `[测试·收尾]` 覆盖层

- **身份**：最终验收 QA。
- **前置**：整体 Code Review 已放行。
- **详细要求**：执行前置用例矩阵，核对自动化、集成、E2E、视觉、可访问性、失败恢复和回归证据。
- **闭环**：发现代码问题则退回程序修复并重新 Review；全部通过后才允许完成专业需求并归档 Room。
