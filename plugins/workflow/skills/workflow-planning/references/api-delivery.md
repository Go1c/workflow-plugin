# 蓝图落单与读回

## 写前准备

1. 先按 `workflow-ops` 的凭证解析顺序取得项目配置，再调用 `/me` 核对用户、项目与角色。
2. 多 profile 且当前目录没有项目绑定时，先让用户选择项目；不得静默写入默认项目。
3. 按线上公开指南与 OpenAPI 现查 `/rooms`、`/requirements`、`/attachments` 的当前字段和权限，不复制本文件里的示意当合同。
4. 列出当前项目 Room，并用 `/search` 查蓝图标题；发现同名或高度相似对象时先报告，让用户决定复用、更新或另建。

## 简单需求

1. 用最终提示词创建一条 Requirement；不显式写 status，让绑定工作流决定初始态。
2. 用户提供原始附件时，上传到该 Requirement。
3. GET 读回 Requirement，并列示附件确认真实落库。
4. 规划阶段不创建 WorkItem，也不进入代码实现。

## 跨工种需求室

1. 创建 Room，名称使用蓝图功能名，描述先写共同目标、工种与“原始需求待创建”。
2. 创建 `[原始需求]` Requirement，并设置 Room 归属。
3. 把原始文件上传到该 Requirement；附件只存一份。
4. PATCH Room 描述，写入原始需求 displayKey 与可点入口。
5. 按蓝图 DAG 的拓扑顺序创建其余 Requirement；渲染每张正文时，把临时前置编号替换成已读回的真实 R-* 单号和标题。
6. 每写一张立即 GET 读回，记录 UUID、displayKey、标题、category、roomId 与链接。

Requirement 当前没有通用的前置关系写接口，规划阶段把依赖写进正文。专业 Requirement 执行并拆成 WorkItem 后，才由排期能力建立结构化依赖。

## 断点续建

- 每次准备重试前，先按已知 UUID GET；没有 UUID 时按标题搜索并核对 Room 归属。
- 已读回成功的对象不得重建。从 DAG 中第一张缺失对象继续。
- 创建下游失败时保留已成功对象，向用户逐条报告部分成功；不得删除或回滚用户可见 PM 数据来伪装原子性。
- 网络错误或 5xx 后先查询是否已落库，确认不存在才重发。
- 422 只按 ProblemDetails 修正一次；再次失败就停止并报告 traceId。

## 收尾

最终报告必须包含 Room（如有）、所有 Requirement、附件、失败项和边界声明。没有读回证据就不得声称创建成功。
