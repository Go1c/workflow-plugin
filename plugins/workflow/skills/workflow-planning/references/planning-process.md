# 固定规划与开发阶段

本文件定义蓝图里的阶段与依赖。规划 Skill 只生成并落单这些 Requirement；真正执行由目标仓库的开发流程负责。

## 需求定义

- 复杂需求第一张固定为 `[原始需求]`，保存输入、附件、讨论结论、范围与非目标。
- 按需生成一张或多张 `[策划]`，锁定用户、流程、状态、权限、内容合同、阶段范围与成功指标。
- 任何会影响下游的产品决定必须在本阶段定稿；不得让设计、QA 或程序自行补产品决定。

## UX/UI 与可选美术

- `[UX/UI]` 消费已锁需求，定义信息架构、逐屏流程、完整状态、文案、响应式与可访问性。
- `[美术]` 在需要游戏资产、品牌视觉或风格交付时生成；与 UX/UI 可在共同策划前置完成后并行。
- 两者必须交付可供 QA 写测试、程序实现的明确规格，不以“参考设计”代替可验收合同。

## 测试·用例先行

- `[测试·用例]` 在任何程序代码之前完成，消费需求、UX/UI 与美术规格。
- 覆盖功能、接口、权限、错误、恢复、兼容、视觉、可访问性、集成、E2E 和回归；只生成适用于本需求的部分。
- 每条程序 Requirement 必须列出自己消费的测试单与具体用例族。

## 程序·协议/公共

- 先锁共享协议、API/DTO、客户端与服务端公共接口、数据模型、公共框架和测试夹具。
- 公共合同是下游共同依赖，未锁定前不得让消费方基于不同猜测并行开工。
- 合同锁定后，文件集不重叠的 `[程序·服务端]`、`[程序·客户端]` 和公共能力可进入同一 wave。

## 程序·功能

- 按独立交付物与文件集拆卡；依赖满足且文件集不重叠的功能卡并行执行。
- 每张程序单强制 TDD：先把对应 QA 用例转成失败测试，确认因缺少目标行为而失败，再写最小实现并使测试通过。
- 实现者自行检查范围、测试和验证证据；开发 wave 内不逐卡派 reviewer。

## 整体 Code Review

- 所有程序卡完成、合并且集成验证通过后，只对基线到完整交付点的完整 diff 做一次整体 Code Review。
- reviewer 对照原始需求、专业需求、QA 测试合同、项目规则和验证证据，输出放行或按严重度分级的 findings。
- 阻断 findings 集中进入一个修复 wave；修复后复跑相关测试与全量验证，再由 reviewer 复核，不拆成每卡审查循环。

## 测试·收尾

- `[测试·收尾]` 只能在整体 Review 放行后开始，执行前置测试合同中的自动化、集成、E2E、视觉与手工验收。
- QA 发现代码问题时回程序修复，并重新经过整体 Review 后再回 QA；不得绕过 Review 直接复验。
- QA 全部通过后，专业 Requirement 转完成，Requirement Room 转 archived，整个大单结束。

## 简单程序需求

简单程序需求不建 Room，但它的一张完整提示词必须包含同一条质量链：QA 用例定义 → 失败测试 → 实现 → 自测 → 整体 Review → QA 收尾。执行阶段可按需要拆 WorkItem，但只做一次交付级 Review。
