# 证据评论模板与交回格式

## 一、完成回写的证据评论（统一结构，让验收方机械核对）

`POST /comments`，`targetType` 按对象取 `requirement` / `work_item` / `bug`，`body` 用下面的 Markdown 模板。小节一个不少：没有内容的写「无」，**不留空标题、不自由发挥**——验收方要拿这份结构逐条对验收项。

```markdown
## 执行交付：<displayKey> <标题>

- 执行者：<Agent 名或脱敏标识>
- 时间：YYYY-MM-DD HH:mm（时区）
- 交付位置：<仓库 + 分支 + 提交号；非代码交付写产物路径与版本>

### 改动清单
- <实际变更，按文件 / 资产 / 配置逐条；含新增、修改、删除>

### 验收对照
按卡上验收项原文与顺序逐条对：
1. <验收项原文> —— 通过 / 未覆盖 —— 证据：<命令 + 关键输出摘要，或截图附件文件名>

### 实际运行的验证
- `<命令>` → <关键输出或结论>
（没跑的写「未执行」；不得用计划中的验证冒充结果——G7）

### 决策记录
- <开工前讨论确认的取舍：问题 → 谁拍板 → 结论>；没有写「无」

### Known gaps
- <未覆盖项、已知风险、依赖的后续单 displayKey>；没有写「无」

### 边界声明
- <本次没做什么；与卡内要求的偏离及原因>；没有写「无」
```

纪律：证据只写实际执行过的命令与真实输出（G7）；不贴 token、凭据、个人数据或整段无关日志（G4）；引用原单附件写文件名，不重复上传。

## 二、模式二（无凭证）的交回报告

执行 Agent 不持凭证时，交回物必须让调度方**不追问一句**就能代写。开工前的需求梳理与决策清单（execute-flow 第四节）作为**中间报告**先交调度方一轮，拿到答复才执行；完成后的会话报告固定五段：

1. **目标单**：displayKey + 标题（派遣 prompt 给了 UUID 就带上）。
2. **建议流转**：完成后建议的目标状态**语义**（如「待验收」）——具体 `toStateKey` 由持凭证方现查 transitions 决定，报告里不猜状态 key（G6）。
3. **证据评论正文**：按第一节模板写完整 Markdown，调度方原样 `POST`，不需要改写。
4. **附件清单**：本地文件绝对路径 + 每个文件证明哪条验收项（调度方按清单上传后，评论正文里的文件名要能对上）。
5. **Known gaps 与边界声明**：与评论正文一致地再列一遍——调度方要据此决定是否流转、是否先退回。

调度方代写时按 [execute-flow.md](execute-flow.md) 第七节的顺序执行并逐步读回；代写完成后把 displayKey + 链接 + 读回结果回给执行侧与用户留档（G3：没读回不说已回写）。

## 三、向用户交回（两种模式通用）

1. 单号 + 标题 + 链接 + 当前状态（模式一写读回确认的状态；模式二写「待调度方回写」）。
2. 已回写 / 待代写的评论与附件清单。
3. 验收对照结论摘要（几条通过、几条未覆盖）。
4. Known gaps 与边界声明。
5. 失败与遗留：没成功的调用列状态码 + `traceId`；部分成功说部分成功。
